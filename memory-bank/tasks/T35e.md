# T35e: Updater Integrity and Release Artifact Consistency

*Created: 2026-08-11 02:03 IST*
*Last Updated: 2026-09-02 15:55:25 IST*

**Status**: 🔄 **IN PROGRESS**
**Priority**: HIGH
**Parent**: T35

## Scope

Strengthen the updater's executable-code trust boundary and ensure checked-in,
local, CI, ZIP, and direct release artifacts describe the same build.

## Acceptance Criteria

- [ ] Verify release asset checksums or signed release metadata before install.
- [ ] Verify downloaded manifest version and plugin identity against release
  metadata.
- [ ] Validate all required runtime files consistently, including versions and
  documentation where applicable.
- [ ] Clean temporary update directories on all success and failure paths.
- [ ] Add rollback coverage after successful installation and reload failure.
- [ ] CI detects drift between source, generated `main.js`, and release assets.

## Investigation Evidence — 2026-08-12

- The Stable channel currently has no published stable release; GitHub's
  `/releases/latest` endpoint returns 404 while the rolling `dev` release is
  available.
- The updater currently converts that failed check into a false "up to date"
  result. This remains an open updater error-reporting fix.
- The committed local `main.js` was briefly built before its final source
  commit, while the CI-published `dev/main.js` correctly embedded the final
  commit. Add generated-artifact identity checking to the acceptance work.
- The successful workflow updated release assets, but the fixed `dev` tag
  metadata still requires verification when the rolling release is updated.

## Implementation Follow-up — 2026-09-02

- Compared the updater with the working implementation in the local
  `obsidian-ai` checkout and ported the shared release-check and diagnostics
  pattern to `obsidian-git`.
- GitHub requests now use cache-busting, validate HTTP status, preserve the
  GitHub error message, and write updater diagnostics through the plugin logger.
- Rolling development updates use the commit recorded in the release body,
  so a reused `dev` tag can still identify a new build. Branch-specific
  `latest-dev-*` releases are selectable and browseable from Settings.
- The build now embeds both commit and branch identity. A feature-branch CI
  workflow publishes matching direct assets for branch builds.
- Verification completed locally: focused updater tests 8/8, full Node suite
  32/32, production build, archive generation, and `git diff --check`.
- Still open: checksum or signed metadata verification, cleanup of temporary
  update directories on every failed download path, and real Obsidian
  desktop/mobile install and reload acceptance.
