# T35a: Credential Safety and Git Staging Boundaries

*Created: 2026-08-11 02:03 IST*
*Last Updated: 2026-08-11 03:12:13 IST*

**Status**: 🔄 **IN PROGRESS**
**Priority**: HIGH
**Parent**: T35

## Scope

Prevent Git credentials and sensitive diagnostics from being persisted,
staged, logged, exported, or pushed unintentionally.

## Acceptance Criteria

- [x] Use Obsidian `SecretStorage` as the primary credential
  boundary, with settings storing only a secret reference; document the
  supported Obsidian version and any verified at-rest limitation.
- [x] Define an explicit unsupported-platform policy; never silently fall back
  to plaintext `data.json`, XOR, Base64, or masked-field storage.
- [x] Migrate legacy plaintext PAT/password settings only after a successful
  secret-store write, then stop creating credential-bearing backups.
- [x] Never stage the plugin's own settings or credential-bearing data file
  through automatic sync.
- [ ] Redact PATs, passwords, Basic Auth values, and embedded URL credentials
  from console logs, notices, exported logs, and error details.
- [ ] Validate and migrate malformed or legacy settings without exposing
  credential values.
- [ ] Add tests proving credentials do not appear in logs, exported files, or
  staged file lists.

## Planned Storage and Git-Credential Design

1. Use Obsidian `SecretStorage` for the current `isomorphic-git` plus
   `requestUrl` transport on desktop and mobile. Resolve the secret only at
   the start of each remote operation; do not retain a plaintext value in
   persisted settings.
2. Use `SecretComponent` for creation, selection, replacement, and deletion of
   the PAT/password reference. Keep the remote URL and username separate from
   the secret. Reject URLs containing embedded user-info credentials.
3. Treat Git credential helpers and SSH agents as related alternatives, not an
   implicit implementation dependency. The current transport does not invoke
   native Git, so `osxkeychain`, Git Credential Manager, and `libsecret` cannot
   be assumed to supply credentials. Revisit them only with a native-transport
   or SSH design under the T34/T35 boundary.
4. Prefer GitHub device flow or another provider OAuth flow for supported hosts
   to reduce manual long-lived PAT entry. T34b owns the GitHub-specific flow;
   T35a owns the storage, redaction, staging, and migration contract.
5. Do not promise cross-device credential synchronization. Secret references
   may sync, but each device must explicitly link or create its local secret.
   Missing-secret and re-link states must be visible and actionable.

## Read-only Audit — 2026-08-11

- `src/main.ts:9-13, 231-236, 623-636` stores the password/PAT in ordinary
  plugin data and saves it on every settings change.
- `src/logger.ts:81-95, 131-172` exports raw messages and data, prints raw
  errors, and includes raw error text in Notices; there is no redaction layer.
- `src/gitManager.ts:21-30, 167, 373-381, 525-545, 1298-1317` logs remote
  URLs and response content while constructing Authorization headers.
- `src/gitManager.ts:893-907` stages every changed path without an explicit
  plugin-state exclusion policy.
- `src/main.ts:326-360, 452-461` updates credentials only during sync; direct
  pull/push commands can continue using a stale GitManager credential object.
- `tests/git-manager.test.mjs:137-147` verifies Basic Auth construction but
  has no redaction, export, settings, or staging-boundary coverage.

## Audit Exit Criteria

- Define the supported `SecretStorage` version and unsupported-platform policy
  before changing settings persistence.
- Add a central redaction test surface before routing more errors through the
  logger or user-facing Notices.
- Add staging-policy tests that include plugin data, updater state, and debug
  exports while preserving deliberate manual staging behavior.
