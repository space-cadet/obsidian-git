# T35c: Repository Initialization and Destructive-Operation Safety

*Created: 2026-08-11 02:03 IST*
*Last Updated: 2026-09-03 16:39:34 IST*

**Status**: 🔄 **IN PROGRESS**
**Priority**: HIGH
**Parent**: T35

## Scope

Make local-only, clone, empty-remote, existing-repository, and remote-error
paths explicit and safe.

## Acceptance Criteria

- [ ] Clone works directly when no local `.git` directory exists.
- [ ] Authentication, permission, network, invalid-URL, and empty-remote
  failures are classified separately.
- [ ] Local-only sync never attempts a remote ref request.
- [x] A failed clone never silently converts into local initialization unless
  the error is classified as an empty remote.
- [ ] Existing `.git` state is not deleted without a verified replacement and
  recoverable backup.
- [ ] Untracked and staged vault files are protected during clone/replacement.
- [x] Interrupted clone and shallow-fetch paths do not delete the only
  recoverable `.git` state; replacement and retry behavior is explicit.
- [ ] Add tests for fresh vault, empty remote, invalid credential, and failed
  clone scenarios.

## Implementation Slice — 2026-08-11

- Added `src/repositoryState.ts` with explicit authentication, permission,
  invalid-URL, network, empty-remote, and unknown classifications.
- Local-only initialization now avoids remote ref requests.
- Fresh-vault manager creation is now read-only; explicit Clone Remote actions
  reach `initializeRepo()` and failed remote clone paths return a safe
  classification instead of silently initializing.
- Existing `.git` replacement and shallow-fetch backup protection remain open.

## Implementation Slice — 2026-08-12

- Fresh and shallow clone now initialize only when the target directory lacks
  `.git/HEAD`, then retain that local state across fetch failure or
  cancellation instead of deleting it.
- Added a regression test for a failed fresh clone retaining `.git/HEAD` and
  `.git/config`.
- Existing-repository replacement, untracked/staged-file protection, and
  protected backup/rollback remain open; this slice deliberately does not
  overwrite an existing repository.
- A completed fetch now leaves explicit recovery metadata until checkout
  succeeds, allowing a retry to resume file checkout without contacting the
  remote again.

## Startup Clone Regression Fix — 2026-08-12

- Sidebar refresh now detects repository state without initializing or cloning.
- `ensureGitManager()` only creates a manager; it no longer calls
  `initializeRepo()` as a side effect.
- Auto-sync skips vaults without an existing `.git` directory.
- Normal sync refuses to initialize or clone; only explicit Clone Remote uses
  the initialization path.
- Added a regression test proving a missing local repository does not contact
  the remote during normal sync.

## Read-only Audit — 2026-08-11

- `src/main.ts:326-335` returns `null` when no local `.git` exists, so
  `syncVault()` cannot reach `initializeRepo()` for the fresh-vault clone path.
  The sidebar's Clone Remote actions at `src/views/GitSidebarView.ts:403-416`
  and `449-462` therefore call a path that currently fails before cloning.
- `src/gitManager.ts:396-419` treats every clone failure as permission to run
  `git.init()` and configure a remote, including authentication, permission,
  invalid-URL, and network failures.
- `src/gitManager.ts:728-738` removes `.git` before attempting a clone when
  there are no local commits, without protecting untracked or staged vault
  files and without a recoverable backup.
- `src/main.ts:366-370` initializes without a state precondition; concurrent
  actions can race with repository detection and initialization.
- `src/gitManager.ts:367-382` changes the configured origin by deleting and
  recreating it when the URL differs, without a validated replacement or
  rollback boundary.
- `src/gitManager.ts:762-763` removes `.git` before the memory-efficient clone
  attempt, while `isomorphic-git` removes its partial git directory when clone
  fails. This leaves interruption recovery undefined and can explain why a
  cancelled or failed operation leaves no local files.

## Audit Exit Criteria

- Model fresh vault, local-only, empty remote, ready, authentication failure,
  remote denial, conflict, and failed-operation states explicitly.
- Allow local initialization fallback only after a verified empty-remote result.
- Never remove existing `.git` or overwrite vault files without a protected
  snapshot and an explicit user-confirmed replacement path.
- Add isolated tests for fresh-vault clone, invalid credentials, network clone
  failure, empty remote, staged files, and existing local repository state.
- Add interruption tests proving the chosen partial-state, backup, retry, and
  cleanup contract for both direct clone and shallow fetch plus checkout.

## Follow-up Issue — Remote browsing and damaged-repository recovery (2026-09-02)

- A configured, reachable remote must remain browseable from the Commits tab
  when the local `.git` directory is missing or damaged. Local repository
  detection must not gate the remote read path.
- `isRepository()` currently treats a readable `.git/HEAD` as sufficient
  presence, which can misclassify a damaged repository as usable. Separate
  repository existence from repository health before choosing local or remote
  behavior.
- Add an explicit Repair/Rebuild Local Repository action. It should construct a
  temporary Git state from the remote, compare its tree with current vault
  files, show local-only, remote-only, and conflicting files, and require
  confirmation before replacing existing `.git` state.
- Existing `.git` state must remain recoverable through a protected backup;
  vault files must not be overwritten as an implicit side effect of repair.
- Add tests for remote commits without `.git`, damaged `.git/HEAD`, failed
  rebuilds, backup retention, and comparison results.
