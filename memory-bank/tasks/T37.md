# T37: Tentative Plugin Rewrite Feasibility and Architecture Assessment

*Created: 2026-09-03 19:58:37 IST*
*Last Updated: 2026-09-04 00:53:16 IST*

**Status**: ⏸️ **TENTATIVE / PLANNED**
**Priority**: MEDIUM
**Parent**: T35

## Scope

Assess whether the Obsidian Git plugin should be incrementally re-architected
or rewritten from scratch using the lessons from the sidebar, staging,
repository-recovery, transport, logging, updater, and mobile incidents. This
task is an assessment and design track, not authorization to replace the
current plugin.

## Why This Task Exists

The reported failures are not isolated presentation defects. They expose
missing boundaries between repository state, asynchronous operations, read
snapshots, cache invalidation, progress lifecycle, persistent diagnostics,
Git-ignore policy, and the Obsidian/mobile filesystem and transport layers.
Repeated fixes can improve the current code, but the long-term cost and risk
of continuing without those boundaries must be measured explicitly.

## Acceptance Criteria

- [ ] Map the current plugin into explicit domain, adapter, transport, UI, and
      persistence boundaries.
- [ ] Identify which existing behavior and public settings/commands must be
      preserved during any migration.
- [ ] Define a conformance suite for status, ignore rules, staging,
      pull/push, recovery, cancellation, caching, logging, and progress.
- [ ] Compare incremental extraction against a clean rewrite using effort,
      regression risk, mobile compatibility, release risk, and rollback cost.
- [ ] Define measurable go/no-go criteria for a rewrite and a migration plan
      that keeps the current plugin usable during evaluation.
- [ ] Record a final recommendation after desktop and mobile acceptance data
      is available.

## Implementation Direction

The default recommendation is incremental extraction behind stable interfaces:
`RepositorySession`, `OperationCoordinator`, `StatusReadModel`,
`CacheStore`, `ProgressController`, `LogStore`, and `GitPolicy`. The existing
UI should consume these boundaries before any replacement is considered. A
full rewrite is justified only if the conformance suite shows that the
current lifecycle and adapter contracts cannot be isolated safely, or if
mobile failures remain architectural after hardening.
