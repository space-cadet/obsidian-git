# T37: Tentative Plugin Rewrite Feasibility and Architecture Assessment

*Created: 2026-09-03 19:58:37 IST*
*Last Updated: 2026-09-04 20:18:35 IST*

**Status**: ⏸️ **TENTATIVE / PLANNED**
**Priority**: MEDIUM
**Parent**: T35

## Scope

Assess whether the Obsidian Git plugin should be incrementally re-architected
or rewritten from scratch using the lessons from the sidebar, staging,
repository-recovery, transport, logging, updater, and mobile incidents. This
task is an assessment and design track, not authorization to replace the
current plugin.

## Why This Task Exists

The reported failures are not isolated presentation defects. They expose
missing boundaries between repository state, asynchronous operations, read
snapshots, cache invalidation, progress lifecycle, persistent diagnostics,
Git-ignore policy, and the Obsidian/mobile filesystem and transport layers.
Repeated fixes can improve the current code, but the long-term cost and risk
of continuing without those boundaries must be measured explicitly.

## Acceptance Criteria

- [ ] List the actual user workflows that still fail or remain untested.
- [ ] Identify which existing settings, commands, UI, and Git behaviour must be
      preserved.
- [ ] Check whether each observed problem can be fixed directly in the current
      implementation without adding a new general-purpose mechanism.
- [ ] Decide whether a replacement is justified by observed behaviour and
      measured maintenance cost, rather than by source complexity alone.
- [ ] Record a small acceptance plan that keeps the current plugin available
      while any replacement is evaluated.
- [ ] Record a final recommendation after the relevant desktop, Android, and
      live-remote evidence is available.

## Implementation Direction

There is no prescribed module list or extraction order. Start with the smallest
direct change that fixes a demonstrated user problem. Reuse the current code
where it already works, and replace only the Git or state-update code that
cannot meet a required workflow without disproportionate complexity.

A replacement is justified only when observed behaviour shows that the current
implementation cannot be made dependable with small, local changes. The
existing plugin remains the comparison and rollback version during that
decision.

## KISS Revision — 2026-09-04

The rewrite assessment is now user-workflow-led. The minimum implementation
questions are whether Git operations can run safely, be cancelled when the UI
offers cancellation, and update the current view without applying an old
result. A global lifecycle event system, source-structure test, and dedicated
sidebar cache are not required unless later evidence proves that a simpler
implementation cannot work.
